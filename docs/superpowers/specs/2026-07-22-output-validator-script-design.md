# Design Spec: Automated C-Code Output Validator Script

This design spec outlines the implementation of an automated test script (`scripts/validate_generated_code.ts`) designed to run immediately after the code generation phase in the ADIA State Machine v3.0 pipeline. It parses the generated C/H code and validates it against the source JSON model to guarantee compilation readiness, runtime correctness, and safety binding directionality.

---

## Technical Approach

### 1. Zero-Dependency AST Parsing Strategy
Instead of relying on heavy native parsing libraries like `tree-sitter` (which require native compiler toolchains to compile C bindings on the host and can fail in environments lacking build tools), we will implement a robust, structured state machine parser in TypeScript. 
Since the code is auto-generated by our own template engine, it adheres to extremely clean, predictable syntax conventions. We can parse:
*   **Enums**: Extract enums (`SM_Node_t`, etc.) by finding `typedef enum { ... } EnumName;` blocks and resolving each identifier's implicit or explicit value.
*   **Structs**: Extract `SM_Data_t` members by identifying `typedef struct { ... } SM_Data_t;` and extracting lines using regex `^\s*(volatile\s+)?([A-Za-z0-9_]+)\s+([A-Za-z0-9_]+);`.
*   **Macros**: Extract `#define KEY VALUE` using line-by-line regex.
*   **Functions**: Extract declarations and definitions by matching signature patterns like `(void|SM_Error_t|SM_Node_t)\s+([A-Za-z0-9_]+)\s*\(([^)]*)\)`.

### 2. Validation Test Cases (TR-01 through TR-07)

*   **TR-01: Duplicate Content Check**:
    *   Assert that `#ifndef SM_CONFIG_H` appears exactly once in `sm_config.h`.
    *   Verify all `#define` macro keys are unique.
*   **TR-02: Enum and Index Alignment**:
    *   Parse enums from `sm_config.h` (e.g. `SM_ST_ACTIVE = 1`, `SM_ST_IDLE = 2`).
    *   Parse index macros (e.g. `#define SM_ST_ACTIVE_IDX 1U`, `#define SM_ST_IDLE_IDX 2U`).
    *   Verify `SM_ST_X` value equals `SM_ST_X_IDX` value.
*   **TR-03: Function Signature Consistency**:
    *   Verify `SM_Init` and all entry/during/exit action declarations and definitions use pointer parameter `ADIA_Instance_t* instance`.
*   **TR-04: Phantom Variable Detection**:
    *   Extract the members of `SM_Data_t` and compare them with the variable list in the JSON model.
    *   Assert that the set difference is empty, and explicitly check that `x` and `state_timer` are not in the struct.
*   **TR-05: I/O Binding Directionality**:
    *   Inspect `SM_Sync_IO` in `sm_core.c`.
    *   Assert that LHS variables in `MCAL_Dio_ReadChannel` assignments are defined as inputs in the JSON model (or have input prefixes/suffixes).
    *   Assert that RHS expressions in `MCAL_Dio_WriteChannel` calls are outputs.
*   **TR-06: Compilation Dry-Run**:
    *   Locate a compiler (`avr-gcc`, `gcc`, or `clang`) on the host system.
    *   Invoke syntax-only compilation checks (`gcc -fsyntax-only` or `avr-gcc -c`) to verify standard compliance.
*   **TR-07: MCAL Interface Contract Validation**:
    *   Assert that all `MCAL_*` functions called in `sm_core.c` have declared inline/prototype definitions in `mcal_dio.h`.

---

## CLI Script Interface

The validation script will be executable from the command line:
```bash
npx ts-node scripts/validate_generated_code.ts --model <path_to_json> --output <path_to_generated_dir>
```

### Output Format
The script will output a clean, color-coded report to stdout and write a summary to `test_results.json`.

*   Exit Code: `0` on success, `1` on validation failures.
