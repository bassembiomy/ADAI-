# Stateflow-Like C99 Code Generation & MCU Delivery Verification Gate

## Executive Summary

This document defines the runtime timing contract, X-Bridges solver loop bounds, state traceability model, and verification evidence boundaries for C99 state-machine packages generated by ADIA.

---

## 1. Embedded Execution Sequence

Every generated package implements the deterministic single-tick embedded loop:

```c
SM_ReadInputs(&instance);
SM_Step(&instance, observed_delta_ms);
SM_WriteOutputs(&instance);
```

### Logical Tick Normalization

- State timers and X-Bridges solvers advance by exactly `SM_TICK_MS` per accepted tick.
- Accepted jitter: observed calls satisfying `abs(delta_ms - SM_TICK_MS) <= SM_TICK_TOLERANCE_MS` (where `SM_TICK_TOLERANCE_MS = max(floor(SM_TICK_MS/10), 1)`).
- Calls outside tolerance latch `SM_ERR_TIMING` and transition to the safe configuration without updating state timers.

---

## 2. X-Bridges Bounded Solver Loop

- Substeps per tick: `SM_XB_<STATE>_SUBSTEPS_PER_TICK = SM_TICK_MS / (solver_step_seconds * 1000)`.
- Generated code emits one static helper function `SM_XB_<STATE>_SolverSubstep(instance)` called within a bounded C loop:

```c
for (xb_substep = 0U; xb_substep < SM_XB_<STATE>_SUBSTEPS_PER_TICK; ++xb_substep) {
    SM_XB_<STATE>_SolverSubstep(instance);
}
```

- Code size: $O(1)$ with respect to `substepsPerTick`.
- WCET: Worst-Case Execution Time scales linearly with `substepsPerTick` and must be evaluated against target MCU timer constraints.

---

## 3. Model-Scoped Metrics & State Traceability

- **Unsupported Embedded Capabilities:** Scoped strictly to operation types used within the model.
- **Operation Evaluations Per Tick:** Computed as $\sum (\text{blocks in state} \times \text{substepsPerTick})$.
- **State Traceability:** Every state maps its user-defined Name, Model ID, C Enum, Layer, and X-Bridges presence in markdown reports and as sanitized C comments preceding state macros and function definitions.

---

## 4. Verification Evidence Taxonomy

| Evidence Label | Scope & Requirement |
|---|---|
| `STATIC_ANALYSIS_ONLY` | Report generated from immutable AST and semantic IR analysis without running executable code. |
| `DYNAMIC_EXECUTION_VERIFIED` | Host compiler (GCC) compiled and successfully executed the smoke test harness (`sm_host_test.c`). |
| `dynamicReachability` | Explicitly recorded when executable reachability suite has run. |
| `differential` | Verified line-by-line trace equivalence between TypeScript interpreter and compiled C execution. |
| `embeddedCompile` | Target toolchain (e.g. `arm-none-eabi-gcc`) compilation status for MCU. |
| `targetHardware` | Hardware-in-the-Loop (HIL) or physical target board verification status. |

---

## 5. Security & Isolation Boundary

- Host smoke verification is executed through an isolated IPC channel (`sm-verify-generated-c`) with least-privilege RLS (`codegen.verify` role: `ENGINEER`).
- Standard payload limits: $\le 32$ files, $\le 2\text{ MiB}$ per file, $\le 16\text{ MiB}$ total, strict filename allowlist, and process execution with `shell: false` in temporary directories.
- Browser/fallback exports default safely to `STATIC_ANALYSIS_ONLY` when host verification is unperformed or unavailable.
