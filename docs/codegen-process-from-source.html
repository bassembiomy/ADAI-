Reading the code generator — source line → emitted C line

This is the code-generation process as implemented, read out of the generator itself. Each generator excerpt below is sliced from the repository at build time; each emitted-C excerpt is the verbatim output of that same code for the demo model. Nothing here was rewritten by hand, and the document cannot drift from the source unless the build itself is re-run: python3 docs/codegen-demo/tools/build_source_doc.py.

The whole generator in one sentence. smCGenerator.ts is a set of pure render functions (renderConfigHeader, renderMappingSource, renderCoreSource, renderSafetySource, renderUserLogicSource, renderMcalHeader, …), each of which walks one slice of the semantic IR and returns a string; generateCArtifacts() calls them, adds the generated test/manifest package, and returns a file list.

The three techniques it uses, and nothing else.

  1. Ordering + indexing — orderedStates()/orderedLayers()/buildIndex() turn model IDs into small integers once; every other function then refers to a state as SM_ST_X and to a state's function as SM_Enter_Deep_7.
  2. One render function per C construct — renderActions(), renderMarkEntered(), renderRouteEnabled(), renderEnterStateAlongPath(), renderRestoreStateBody(), renderCommitRoute(), renderTransitionPhase(), renderExecuteFunctions(), renderExitFunctions(). Each takes IR objects plus an indent string and returns source text.
  3. Emit when the IR says so — a construct exists in the C output iff a condition on the IR is true: state.childLayerIds.length > 0, state.activeSlot >= 0, layer.activeSlot !== null, route.destinationKind === 'history', ir.activeSlotCount > 0, ir.ioMappings.length > 0, ir.verification.cStandard === 'c90'. This is why a small model produces a small file.

Why the generated C is deterministic. Every iteration order is defined by an explicit sort (activityIndex, activeSlot, priority, localeCompare), every name comes from toCIdentifier(), and no render function reads the clock, the environment or a random source — the emitted bytes are a function of the IR alone.

1Identity: model IDs → C symbols

Everything downstream depends on this first decision: a state or layer must be addressable by a small integer that is stable for a given model and consistent across the four files that reference it. The generator never emits a UUID; it emits names derived from the model ID plus an order derived from the IR.

1.2 Where the IR values come from

builder smSemanticBuilder.ts — state lowering

generated production/sm_config.h

Read the two sides together: enumName and activityIndex come from the builder, and the header renderer only walks states/layers in their sorted order, assigning stateOffset + 1 to the enum and index.stateNumber to the _IDX macro. Consequences visible in the output:

  • Zero is reserved. SM_NODE_INVALID = 0 and states start at 1, so a zeroed instance means "no state", and bool state_active[SM_NUM_STATES + 1U] can be indexed by a raw enum value.
  • The same number appears twice on purpose — as a macro (#define SM_ST_FAN_LOW_IDX 8U) for compile-time array sizing and constant folding, and as an enum member (SM_ST_FAN_LOW = 8) for type-checked comparisons.
  • Capacity macros are derived, not configured: SM_NUM_STATES, SM_NUM_LAYERS and SM_NUM_ACTIVE_SLOTS are states.length, layers.length and ir.activeSlotCount.
  • The tick window is computed from two model fields by the ternary in renderConfigHeader: tolerance = tickToleranceMs > 0 ? tickToleranceMs : max(1, floor(tickMs/10)), giving SM_TICK_MIN_MS = tickMs − tolerance and SM_TICK_MAX_MS = tickMs + tolerance (10 ± 1 ms here).

1.3 Identifiers that must be safe

Model IDs are free text (spaces, dashes, unicode, leading digits). Two helpers sanitise them before they reach C:

toCIdentifier() replaces every non-[A-Za-z0-9_] character with _ and prefixes a leading digit — this is the function used for state enums, layer macros, function suffixes and trace IDs. Where a globally visible identifier is needed (X-Bridges block symbols, integration symbols), the stricter allocator in smCIdentifierPolicy.allocateExternalIdentifiers() adds a deterministic SHA-256 suffix truncated to the platform's significant-character limit (default 31) so two long names can never collide after truncation. Internal names can collide only in ways the validator has already rejected.

2Structure: hierarchy → tables and indices

The hierarchy exists in the model as parentId strings. In the C output it becomes: one array slot per OR layer, one boolean per state, and two constant tables. The allocation rule is a two-line predicate in the builder — and its else branch is meaningful (AND layers and empty layers get null, i.e. no RAM).

builder smSemanticBuilder.ts — slot allocation

generated production/sm_mapping.c

Reading the table pair: SM_State_Parent_Layer_Map answers "which layer owns this state" (used by the mapping validator), SM_State_Active_Slot_Map answers "which active_states[] word tracks it" (-1 = none), SM_Layer_Parent_State_Map answers "which state contains this layer" (used by the consistency checker to decide whether a container is active), and SM_Layer_Active_Slot_Map is -1 exactly for the AND layer. Four tables, one question each — no runtime graph traversal anywhere.

The slot test is also a RAM budget

Instance RAM is 2 × SM_NUM_ACTIVE_SLOTS × sizeof(SM_Node_t) for the active/history words, SM_NUM_STATES + 1 bools, (SM_NUM_STATES + 1) × 4 bytes of timers and SM_NUM_LAYERS × (SM_NUM_STATES + 1) bytes of deep-history bits. For this model that is 16 + 16 + 11 + 44 + 55 bytes of machine state on top of SM_Data_t (32 bytes) → sizeof(ADIA_Instance_t) = 184 bytes on the host ABI.

Layers are also where default entry is decided, at generation time: the builder picks the first autostart child, else the first autostart junction, and the renderer then hard-codes that decision into a single call.

Two layers, three lines of C: the OR layer with two children becomes one call to the chosen default, and the AND layer becomes both regions in declaration order. There is no loop and no lookup — the decision that took a priority sort in the builder is now a straight-line statement.

3Control flow: states and transitions → functions and ifs

This section is the heart of the generator. Three things produce the entire tick path: renderTransitionPhase() (guard → action), renderExecuteFunctions() (layer dispatch → state body), and the public-API block inside renderCoreSource(), which emits SM_Step as a literal string array with exactly two interpolations. Each is a loop — or a straight list — over IR-derived data, appending source text.

3.1 A transition: a guard, a path, a commit

The builder classified every authored transition into one of four kinds and expanded it into one or more routes; the moment the runtime takes the transition, each route contributes its exit list, entry list, an LCA (least common ancestor) and, for history targets, a restore instead of a default entry. The emitter turns a route into statements in this order: record history on the states being left → deactivate them → mark the target active → assign the active slot → call the entry chain.

Two things to notice in the emitted code, both visible in the source above. First, the restore chain is emitted inline in the transition (lines 754–761), not inside SM_Restore_State_3 — the transition needs the restore in context of the entry it just performed. Second, the generated indentation of the } else { is uneven (} else if) because lines() joins a conditional branch that has its own indent with a literal else string; it is cosmetic, and the same shape appears in SM_Restore_State_4 above. 3.2 Dispatch: which state runs this tick

The generated control flow is a two-level dispatch and nothing else:

  1. OR layer → switch on the active slot. Exactly one child is active, so the runtime cost is one switch — no candidate scan, no priority loop. The default: return false; arm makes a corrupted slot a no-op rather than a crash.
  2. AND layer → literal ifs, one per region, in declaration order. No slot exists, so every region is tested via state_active[], and after each region runs, the container is re-checked (if (!instance->state_active[...]) { return transitioned; }) — that is how a transition taken inside region 1 stops region 2 of the same parent from executing in that tick. The re-check is emitted only when layer.parentStateId !== null.
  3. State body: transition phase (outer) → _During() → transition phase (inner) → child layers → return. Outer before During and inner after is the ordering that makes an inner transition observable in the same tick while an outer transition still sees the pre-transition output.
  4. Terminal states emit a stub. state.terminal — set by the builder from the model's own isTerminalState flag, not inferred — short-circuits the whole body into (void)instance; return false;: the state can be entered and its entry/exit hooks run, but it can never fire a transition out of itself. This model declares no terminal state, so every state above gets a full body; a model that does declare one loses that state's _During() call entirely, which is the intended "final state" semantics and a regular source of surprise.

3.3 The tick: where all of that gets called

Read the emitted SM_Step against the render function: the guard ladder is emitted in a fixed order (null instance → fault latch → tick window → consistency), then the timer loop, then the execute call. The loop is emitted with a saturating add rather than += (an embedded run of centuries must not wrap uint32_t), advancement is SM_TICK_MS and not delta_ms, and delta_ms is only ever checked against the window. That last point is the single most consequential semantic in the file: logical time is quantised to the tick period, so a non-conforming delta_ms is a fault, not a scaled step.

The same fault-first pattern is repeated in SM_WriteOutputs so that outputs can never be written from a faulted instance; here it reduces to (void)instance; because this model declares no output mappings — the IO statements are generated per mapping in renderCoreSource() itself (§4.4), so an empty mapping list produces an empty function body plus the fault checks.

4Behavioural hooks: entry, exit, history, safety, IO

The generator deliberately splits the model into two kinds of C: the kernel (sm_core.c, sm_safety.c, sm_mapping.c) which is regenerated wholesale, and the hands (sm_user_logic.c) which the kernel calls but the generator only scaffolds. This section follows the hook render functions.

4.1 Entry / during / exit: one function per (state, phase)

Reading the emitted file against the model: the during text of a state is parsed by smExpressions and re-rendered as C (duty_cmd + 1U → (uint16_t)((instance->data.duty_cmd + 1U))), while empty phases still get a function whose body is (void)instance;. Three points the generator is making with this design:

  • Stable hook ABI. The signature is always void SM_ST_X_Phase(ADIA_Instance_t *), so user code can be hand-edited or replaced and the regenerated kernel still links. The header sm_user_logic.h is regenerated too (with a /* State: … | Model ID: … | C enum: … */ comment for each group), but the bodies are plain scaffolding you are expected to own.
  • Conversion at the edge only. Every action assignment is wrapped in the variable's declared C type (renderCType) — that is the entire type system of the emitter: names are checked against ir.variables (an undeclared target is a build-time throw from renderCAction, not a broken build later), and arithmetic happens in the C type of the left-hand side.
  • Trace calls ride along. Each rendered action block also emits SM_TraceAction(instance, "during:PWM_LOW") when a trace label exists, which is how the differential harness (§5.4) can compare interpreter and C traces at action granularity.

4.2 Exit: the history recorder is the interesting half

The emitted SM_Exit_State has exactly three jobs, and the first one is the whole history mechanism. It opens with if (record_containing_layer) { switch (state) { case SM_ST_X: SM_Record_Layer_History(instance, SM_LYR_…); … } }: the flag is passed true only by a transition that is leaving the layer that contains the state, so the recorder writes the deep-history bit for the exact set of states that were active at that moment — one boolean per (layer, state) pair, no lists, no allocation. Then comes an idempotence guard (if (!state_active[idx]) break;), then the recursive exit of child layers for container states, the user _Exit() hook, clearing of the flag and timer, and finally if (active_states[slot] == state) active_states[slot] = SM_NODE_INVALID; — compare-before-clear, so exiting an already-exited state cannot corrupt the slot used by the parent's switch.

The companion block in the same slice is the no-history wrapper: SM_Exit_Layer_No_History_<n> exits a layer's current occupant with record_containing_layer = false. Those wrappers are never called by the state machine; they are referenced by SM_Init with the famous no-op statement form (void)SM_Exit_Layer_No_History_0; (28 such lines in SM_Init, one per generated emitter) purely so that -Wunused-function under -Werror cannot reject a model whose shape leaves one of the generated helpers unreachable. That is a small but characteristic detail of this generator: the strict-warning policy is paid for in emitted bytes.

4.3 Safety: validate the instance, then fail safe

The safety file is generated unconditionally and is the only place that inspects the instance's internal consistency: five clauses in SM_Validate_State_Consistency — (1) every active state's parent must be active, (2) its active_states[slot] word must equal it, (3) every layer whose container is active and that owns a slot must have a valid occupant, (4) that occupant must be a child or descendant of the layer, (5) the layer's own slot word must agree. Any violation returns SM_ERR_CONFIGURATION, which SM_Step turns into a latched fault. The demo model exercises this path: writing an illegal word into active_states[] and stepping once returns SM_ERR_CONFIGURATION (3) and latches the fault, as recorded in the differential evidence.

SM_ApplySafeOutputs() here is three lines — (void)instance; plus MCAL_ApplySafeOutputs(); — because the model sets safetyMode: true (so the MCAL hook is called) but declares no output mappings (so there are no per-channel safe values to write first). Add write mappings with safeValue and the same function grows one MCAL_Dio_WriteChannel(MCAL_CH_…, false) per channel, in mapping order, before the blanket hook — the emitter's mappedOutputs.length === 0 ? … : … ternary is the entire policy switch.

4.4 IO mapping: one line per channel, with x bound to the raw read

This is the one place where the generator does real expression surgery rather than string building. A mapping's conversionExpression (e.g. x * 4095.0 / 100.0) is rendered by renderCExpression with a name-binding callback: any identifier named x is substituted by the raw channel access (MCAL_ReadChannelValue(MCAL_CH_TEMP_ADC) on read, instance->data.duty_cmd on write). The whole statement is then cast to the variable's C type. Two consequences worth stating plainly:

  • Conversion expressions are compiled into the kernel, not into user logic — so the scaling is regenerated from the model and cannot drift from it, and it costs no function call.
  • Because x is a binding by name, the same expression source works for read and write directions; declaring a model variable literally named x in a conversion expression is therefore a name collision to avoid (the callback wins).

In sm_core.c the loop that consumes these lists is literally readMappings.length === 0 ? ' (void)instance;' : …, which is why this model's SM_ReadInputs/SM_WriteOutputs are fault-guarded no-ops: it exercises the empty branch of the IO emitter. Channel macros themselves are emitted into mcal_dio.h by renderMcalHeader — MCAL_CH_* as sequential integers, sorted by channel id for determinism, with prototypes only (the generated header never contains an implementation; the MCAL is firmware you supply).

4.5 The instance layout: where every byte of RAM is decided

Every array in the struct is dimensioned by a macro the same header defines, so the RAM footprint is a direct function of the model's shape: states × 1 B (active) + states × 4 B (timers) + slots × 2 × 2 B (active/history words) + layers × (states+1) B (deep history) + sizeof(SM_Data_t). Adding a 30th state to a model is not free RAM — it is 5 bytes plus one more enum member and one more _IDX macro, with no code change anywhere else. That property (shape → table sizes, generated once, checked by the mapping validator at SM_Init) is what lets the same generator target 32-bit MCUs and a host test build with no configuration.

5Delivery: how the file package is assembled and verified

Everything so far produced strings. This section is about turning strings into a deliverable: naming the files, deciding which ones exist at all, deriving the test plan from the same IR, and then trying to falsify the result.

5.1 One entry point, two package shapes

Three structural facts follow from those forty lines, and they are easy to miss when reading the walkthrough of a running app:

  1. The layer is a pure function of the IR plus options. Nothing here touches the filesystem, the editor or the model JSON — writing files is the caller's job (in this repo, the workspace writer and the app's export path). That is why the same call can be used by the CLI, by tests with an in-memory list, and by this document's evidence driver.
  2. Conditional files exist only when their precondition holds: sm_xbridges.{h,c} only if some state has xBridges, mcal_dio_test_stubs.c only with includeTestShims, sm_host_test.c only with includeHostHarness. This model gets neither X-Bridges nor shims, which is why its production package is exactly the ten files below.
  3. The two shapes differ in more than naming. With includeVerificationPackage: true the function returns at files: packageFiles (27 files, production/ + tests/ + verification/) and never runs the structural self-check; the flat shape (12 files) runs verifyGeneratedCStructure() over its own output. The 27-artefact deliverable is therefore the one that is not self-checked — see §5.3.

5.2 The test package is derived from the same IR that produced the C

The test generator never parses C and never re-reads the model: buildSMTestManifest() walks the IR — states, layers, transitions with their guards and actions, history junctions, verification config — and emits operations (init, set-variable, step, sync-io, fault injection) and expectations (active-state, inactive-state, variable-value, transition-fired, error-code, history). The suite renderer then turns each operation into a call and each expectation into an ADIA_Assert* line, with __FILE__ and __LINE__ captured at the assertion site — so a failing generated test points at generated code, not at a helper. The default-initialisation case asserts the four active states the model starts in, all six variable defaults, the error code and the fault flag without a single hand-written expectation.

One shape detail worth noticing in that loop: the suite list is hard-coded at nine, and a suite with no cases still gets a file with an empty body (int run_suite_io(void) { return 0; }). The generator prefers a stable file set over a minimal one — the runner in test_main.c is generated against the same nine names, so the package shape does not change when a model gains or loses, say, an IO mapping. The cost is nine translation units even when eight of them are the entire test plan.

5.3 The self-check, and what it cannot see

The generator does have a semantic self-check: it extracts the SM_Data_t members from the emitted header with a regex and cross-checks every …->data.member access in the emitted sources, reporting GEN_C_UNDECLARED_DATA_MEMBER as an error. Run against this model's own package, though, all three of its blind spots line up. The driver in docs/codegen-demo/tools/probe_selfcheck.ts prints:

  • It is not run in package mode — the early return at §5.1 means the delivered shape is unchecked.
  • It only scans the file list it was handed — in flat mode that list is the 10 implementation files, so the test sources are never in scope.
  • Its access regex requires a pointer (\w+->data\.\w+), but generated tests declare the instance on the stack and write instance.data.x. Even re-running the checker over the whole 27-file package returns valid=true.

5.4 The proof that the C behaves like the model

compileAndRunCTrace() is the part of the harness that actually closes the loop: it writes the package plus a generated scenario harness, compiles it against the host compiler, runs it, and returns one observation frame per tick with the same shape the interpreter produces (runInterpreterTrace()). compareSemanticTraces() then diffs the two frame arrays field by field. For the 28-step scenario in docs/codegen-demo/generate.ts — idle, start, 20 ticks, over-temperature, resume, stop — both sides produce 29 frames and divergence: null. 5.5 How the pipeline judges the result — and where it does not

deriveAcceptance() is strict in the right way: any FAIL rejects, and nine gates must be PASS (structural, semantic, test-generation, host-compilation, host-runtime, sanitizers, statement-coverage, branch-coverage, differential). The problem is what the pipeline puts into that ninth gate. Gate 8 computes the reference trace, maps it to observations, and then calls compareCycleObservations(refObservations, refObservations) — it compares the reference to itself and never compiles or runs the generated C. The comment on that line ("Exact match with verified candidate observations") describes the intent; the code produces a tautology that can only say PASS, and deriveAcceptance() treats it as one of the mandatory gates. Two consequences:

  • npm run verify:sm:codegen (which drives runVerificationPipeline) can report acceptance: true without any behavioural evidence at all — the C package is verified for compilation, not for equivalence.
  • The real differential exists in this repo, one layer down: compileAndRunCTrace() + compareSemanticTraces(), the path used by §5.4 and by the committed evidence. Wiring Gate 8 to that path (candidate = C observations) instead of to refObservations would make the ninth gate mean what its name says.

A related traceability gap: ir.modelHash is a constant. The builder writes modelHash: "0000000000000000" (smSemanticBuilder.ts:825), and every consumer — the manifest, the differential context, the reports — carries that literal through, so no artefact records which revision of the model it was generated from. Recomputing the hash from the frozen IR at that one site would bind the evidence to the model for free.

6What the generator does not do

The clearest way to describe a generator's contract is by its refusals. Reading all 1,963 lines of smCGenerator.ts, these are the boundaries it deliberately draws.

6.1 No ambient context, no build system, no target

  • It never reads a file, the clock, the environment or a random source. Every render function takes (ir, index) and returns a string; generateCArtifacts() takes the IR and options and returns a file list. The same IR always produces byte-identical files, which is what makes the golden snapshot test meaningful and makes the evidence in this document reproducible.
  • It does not emit a build system. No Makefile, CMakeLists, linker script, startup code or ISR wiring is produced — the package is ten translation units that you compile with your own flags. The pipeline supplies the host flags for testing only (-std=c99 … -Werror …); the target flags are yours.
  • It does not write the MCAL. mcal_dio.h contains channel macros and prototypes; the .c is firmware. A flat package therefore does not link on its own (undefined reference to MCAL_ApplySafeOutputs), which is why the harness generates a stub for host tests.
  • It uses no compiler extensions. Grepping the generator for malloc, free, __attribute__, #pragma, volatile and assert returns zero occurrences of each; the emitted code is fixed-size arrays, uintN_t, bool and memset. There is no heap, no recursion beyond the statically-known layer nesting, and no function pointers except the optional trace sink.
  • It knows the C rules that bite — the instance declares active_states[(SM_NUM_ACTIVE_SLOTS > 0U) ? SM_NUM_ACTIVE_SLOTS : 1U] rather than a potentially zero-length array, SM_Data_t members are emitted in localeCompare order for stable diffs, and ir.verification.cStandard === 'c90' switches every designated initializer to positional order (four sites: renderConfigHeader, renderMappingSource, renderSafetySource, the test suites).

6.2 The expression boundary: validated writes, blind reads

Two asymmetries live in those thirty lines and they explain most of the failure modes you can meet at a C compiler:

SituationWhat the emitter doesWhere the error surfaces

guard reads an undeclared nameparseCondition resolves it to {id: name, cName: toCIdentifier(name)}, and renderNode emits instance->data.name uncheckedC compile time (or never, if the raw name happens to be a member)

That last row is the honest statement of the type system: the generator is a syntax-directed translator with declared types, not a type checker. Integer promotion and overflow analysis are out of scope; the validator upstream (smSemanticValidator.ts) is where a model gets rejected before it ever reaches this file.

6.5 What this walkthrough proves, and what it does not

Proved here

  • The mapping model → IR → C is deterministic and mechanical: every emitted line is traceable to a render function and an IR field.
  • Conditional emission is exact: a smaller model really does emit fewer constructs, not disabled ones.
  • The compiled C and the interpreter agree on a 29-frame scenario with a deep-history restore and an AND region (differential, §5.4).
  • The generated test package is derived from the same IR and carries case → requirement traceability.
  • Regeneration is reproducible: re-running the driver rebuilt all 28 evidence files byte-for-byte identical (md5-verified), including the 29-frame differential trace.

Not proved here

  • No formal equivalence. Differential agreement on one scenario is evidence, not proof; the harness can only cover the vectors you give it.
  • No target compilation, no MISRA, no static analysis. clang/cppcheck/arm-none-eabi-gcc were unavailable in this environment, so those gates were NOT_RUN; only the host compiler ran.
  • No MC/DC. gcov on the host cannot provide it, and the pipeline marks it NOT_APPLICABLE unless the model requires it.
  • Not the whole app. This is the emitter path (smCGenerator + builder + harness); the editor UI, the exporter and the React trace viewer are outside its scope.
