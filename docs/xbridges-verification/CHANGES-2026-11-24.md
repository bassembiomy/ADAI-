## 1. Behaviour changes you can test in the app

### 1.1 XBV-417 — algebraic loop tolerance and iteration limit in the canvas

Simulink exposes the algebraic loop solver in its configuration parameters; ADIA had the two settings in the engine but
nothing on screen to edit them, and the canvas never passed them. They are now real, editable, saved fields.

| What | Where |
| --- | --- |
| Two new toolbar fields, **Loop Tol** (default `1e-6`) and **Loop Iter.** (default `100`) | X-Bridges toolbar, next to the solver options |
| They apply to **every** solver (Euler, RK4, ode23, ode45, ode23tb, ode14x, …) | a loop is solved at every major step, fixed or variable step |
| Invalid input is refused, never clamped | empty, `0`, negative or non-numeric → red field, red message, run refused with `STIFF_SOLVER_INVALID_OPTION` |
| Both are saved with the model, and changing them resets a running simulation | model persistence + the simulation key |

**How to test (5 minutes)**

1. Build `Constant(1) → Sum(++-) → Product(y,y) → Gain(1e-6) → back into Sum`. This is `y = 1 + y − 1e-6·y²`, whose
   solution is `y* = 1000`.
2. Run with RK4. Read the loop signal: `1000.0000` (within `1e-6` relative).
3. Set **Loop Tol** to `1e-2` and run again: it still converges, but with a visibly looser loop error — that is the
   tolerance doing its job.
4. Set **Loop Tol** to `0`, or **Loop Iter.** to `0` or `2.5`. The field turns red, a message appears under it, and the
   run is refused with `STIFF_SOLVER_INVALID_OPTION`. Nothing is silently fixed up.
5. Save the model, reload it: both values come back.

The same case with **Loop Iter.** at `3` on a deliberately slow loop reports `ALGEBRAIC_LOOP_NOT_CONVERGED` (naming the
loop blocks) instead of running on with a fixed point it never reached.

Files: `src/engine/xbridges/simulationConfig.ts` (`algTol`/`maxIter` in `XSimulationConfig`, in `DEFAULT_SOLVER_OPTIONS`,
in `SolverOptionTexts`, in `invalidSolverOptionTexts` and in `solverOptionsForRun`),
`src/components/xbridges/XbridgesWorkspace.tsx` (the two inputs and the simulation key).

### 1.2 WP-23 — the deliberate differences from Simulink are now in the help

The help used to describe the blocks without saying where ADIA intentionally departs from Simulink. Each difference is
now attached to the block it changes, so the block reference tells the whole story. A difference that would be a defect
is deliberately **not** recorded here — it goes to the ledger as a finding.

| Decision | Difference | Shown on |
| --- | --- | --- |
| D9 | Embedded tick time base: every block in tick *k* sees `t_k`; a continuous state publishes at `t_k` and updates to `t_(k+1)` after all outputs | Integrator (continuous) |
| D12 | Rate Limiter has an explicit `initialCondition` (default 0) that Simulink lacks, and its first output differs by sample time | Rate Limiter |
| D15 | Fixed-step solvers do **not** locate zero crossings (Simulink's default for fixed step); adaptive ones do | Relay, Dead Zone |
| D17 | The diagonal blocks follow MATLAB `diag`, so the input shape decides the direction | Diag, MatrixDiag, DiagExtract, ExtractDiag |
| D18 | The robot occupancy grid is updated once per **major step**, not at every solver stage | Robot Vacuum SLAM, Robot Vacuum Mapping |

There is also a new help topic, **`xbridges:SolverPaneDifferences`**, that gathers the solver-side differences in one
place: D15 (fixed-step zero crossings), zero-crossing tangency, the D19 output grid, the XBV-417 loop fields, D9, and gate
G being pending (D4).

**How to test (2 minutes)** — open Help, search "SolverPaneDifferences" (or browse to a Relay and read its Behaviour
section), and check that the paragraph matches the behaviour you can see on the canvas. The relay example in the topic
is runnable: Relay with `switchOn 0.25`, `switchOff 0`, under RK4 and under ODE23 — the fixed-step run switches at a major
step, the adaptive run locates the crossing.

Files: `src/help/blockGuidance.ts` (the `SIMULINK_DIFFERENCES` record and its apply loop, the D18 sentences written

### XBV-436 — far algebraic-loop roots: **still open**

Your decision (D21) was "fix it": make the globalised Newton phase scale-invariant, with acceptance for both wirings at
roots 1e9 and 1e10. **I did not land a fix.** I implemented and measured nine candidate fixes against a 14-case matrix,
and reverted every one; the engine is byte-identical to the branch point (`git status` clean, verified by re-running the
matrix). Being straight about it: the half-day estimate in D21 was wrong.

Measured failure matrix (`y = c + y −/+ k·y²`, zero start):

| Case | `'++-'` + Gain `+k` | `'+++'` + Gain `−k` |
| --- | --- | --- |
| root 1e7, 1e8 | converges | converges |
| root 3.16e8 (`c=1e-3, k=1e-20`) | **fatal** | **fatal** |
| root 1e9, 1e10 | converges | **fatal** |

Every failure is an honest `ALGEBRAIC_LOOP_NOT_CONVERGED` — no wrong value is ever carried on.

Root cause, measured: at the zero start the `y²` column of the Jacobian is **pure rounding** (±1e-12 in one wiring,
±1e-20 in the other), so the Newton step is 1e12–1e19 times the iterate, no line search accepts it, and the perturbation
guard fires. The path that *does* rescue the 1e8 cases is an absolute-residual line search, and it stalls at ~1e4 once
the raw component reaches 1e20.

| Fix tried | Result |
| --- | --- |
| Column equilibration of the direction | fixes `'++-'` up to 1e10, not `'+++'`, not 3.16e8 |
| Relative-residual merit `|g|/(|z|+|F|)` in both line searches | same split |
| Natural-monotonicity test in the scaled variables | no change |
| Trust radius on the Newton step | no change, breaks the 1e3 case |
| Retry Newton after the damped phase | no change |
| Perturbation-first on a degenerate Jacobian | regresses passing cases |
| Perturbation cap | regresses (down to 0.16 on the 1e3 root) |
| Forced Levenberg-Marquardt | regresses |
| Trust-region LM globalisation on the relative merit | regressed every far-root case (0.23) |

**Revised estimate: 1–2 days.** What it needs is not a local scaling change but a redesigned globalisation — a properly
normed trust-region / least-squares formulation with a step bound proved to accept a scale-invariant step, or NLEQ-ERR
implemented exactly as published — developed against the 14-case matrix above with the XBV-431 cases (roots up to 1e8,
both wirings) kept green. All of that, including the table, is in D21.

### XBV-434 — float32 semantics: open, decision taken (D20)

You chose option A (follow Simulink `single`: round after **every** operation). Not started: the generated C carries
every value as `double`, so per-operation rounding needs float temporaries and float prototypes in the generator, and the
interpreter would need every multi-operation block (Sum, Product, matrix products, filters, PID, the integrator's
`x + dt·u`) to round between its arithmetic steps. Landing it half-way would leave the interpreter and the generated C
disagreeing, which is worse than the current single documented profile. **Acceptance to write first:** Sum
`16777216 + 1 + 1 = 16777216`; float accumulation in Product, MatrixMultiply, the filters and the integrator; `sinf`
against `(float)sin`; and the same through the generated C harness. **Estimate: 1–2 days.**
