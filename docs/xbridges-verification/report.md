## Open decisions

- **D20 - XBV-434 float32 semantics.** OPEN - decided in principle, implementation not started (scope: 1-2 days). The user chose option A: follow Simulink 'single' and Embedded Coder, so a float32 signal rounds after EVERY operation instead of once per signal / state write (Sum 16777216 + 1 + 1 must give 16777216, not 16777218), in the interpreter and the generated C alike, with float libm (sinf, powf, expf, logf) against (float)sin, and VectorPow's C aligned (its C already uses powf while the interpreter rounds a double pow). Why it is not done in this pass: the generated C carries every value as `double` (SM_XB_ConvertFloat32 wraps a double result at each write), so per-operation rounding needs float temporaries and float prototypes in the generator, not a local edit; and the interpreter would need every multi-operation block (Sum, Product, matrix products, filters, PID, the integrator's x + dt*u) to round between its arithmetic steps, which is 231 execute functions to audit against Simulink. Doing it half-way would leave the interpreter and the generated C disagreeing, which is worse than the current single, documented profile. The acceptance to write first: Sum 16777216 + 1 + 1 = 16777216; float accumulation in Product, MatrixMultiply, the filters and the integrator; sinf against (float)sin; and the same cases through the generated C and its compile-and-run harness.
- **D21 - XBV-436 far algebraic-loop roots.** OPEN - investigated a second time on 2026-11-24, still not implemented (the first estimate of half a day is now measured as 1-2 days of algorithm work; see the end of this record). The user chose to make the globalised Newton phase scale-invariant rather than document the limitation. Measured failure: y = c + y -/+ k y^2 from a zero start reaches the root for k >= 1e-16 (roots up to 1e8) in both wirings; at 1e-18 / 1e-20 (roots 1e9 / 1e10) only the '++-' + Gain +k wiring converges, and y = 1e-3 + 1e-20 y^2 (root 3.16e8) fails in both. Every failure is an honest fatal (no false root). Root cause, measured this pass: at the zero start the Jacobian is exactly rank deficient on the y^2 column (that column is 0, its finite differences are pure rounding, +-1e-12 for '++-' and +-1e-20 for '+++'), so the Newton step is 1e12-1e19 times the iterate, no line search accepts it, and the perturbation guard fires; the accept path that then works for 1e8 is an absolute-residual line search that stops making absolute progress at 1e4 when the raw component reaches 1e20. Tried and measured (each reverted, no partial change left in the tree): column equilibration of the direction (d_j = 1/max(|J_ij|, rounding floor)) - fixes the '++-' wiring up to 1e10 but not the '+++' one, and does not touch the 3.16e8 case; a relative-residual merit |g_i|/(|z_i|+|F_i|) in both line searches - same split; the natural monotonicity test measured in the scaled variables - no change; a trust radius on the Newton step - no change (and it breaks the 1e3 case); retrying Newton after the damped phase instead of breaking out - no change; perturbation cap, perturbation-first on a degenerate Jacobian, forcing Levenberg-Marquardt - all regress cases that pass today (down to 0.16 for the 1e3 root); and a trust-region LM phase on the relative merit as the globalisation - regressed every far-root case (0.23). Conclusion: the remaining fix is not a local scaling change; it needs a redesigned globalisation (a properly normed least-squares/trust-region formulation with a step bound proved to accept a scale-invariant step, or the NLEQ-ERR natural-monotonicity test implemented exactly as published), developed against the 14-case matrix above with the XBV-431 cases (roots up to 1e8) kept green. The half-day estimate in D21 was too optimistic: budget 1-2 days. Until then the finding stays open, and the help documents the current single documented profile.

- **D21** (2026-11-24, XBV-436 far algebraic-loop roots): OPEN - investigated a second time on 2026-11-24, still not implemented (the first estimate of half a day is now measured as 1-2 days of algorithm work; see the end of this record). The user chose to make the globalised Newton phase scale-invariant rather than document the limitation. Measured failure: y = c + y -/+ k y^2 from a zero start reaches the root for k >= 1e-16 (roots up to 1e8) in both wirings; at 1e-18 / 1e-20 (roots 1e9 / 1e10) only the '++-' + Gain +k wiring converges, and y = 1e-3 + 1e-20 y^2 (root 3.16e8) fails in both. Every failure is an honest fatal (no false root). Root cause, measured this pass: at the zero start the Jacobian is exactly rank deficient on the y^2 column (that column is 0, its finite differences are pure rounding, +-1e-12 for '++-' and +-1e-20 for '+++'), so the Newton step is 1e12-1e19 times the iterate, no line search accepts it, and the perturbation guard fires; the accept path that then works for 1e8 is an absolute-residual line search that stops making absolute progress at 1e4 when the raw component reaches 1e20. Tried and measured (each reverted, no partial change left in the tree): column equilibration of the direction (d_j = 1/max(|J_ij|, rounding floor)) - fixes the '++-' wiring up to 1e10 but not the '+++' one, and does not touch the 3.16e8 case; a relative-residual merit |g_i|/(|z_i|+|F_i|) in both line searches - same split; the natural monotonicity test measured in the scaled variables - no change; a trust radius on the Newton step - no change (and it breaks the 1e3 case); retrying Newton after the damped phase instead of breaking out - no change; perturbation cap, perturbation-first on a degenerate Jacobian, forcing Levenberg-Marquardt - all regress cases that pass today (down to 0.16 for the 1e3 root); and a trust-region LM phase on the relative merit as the globalisation - regressed every far-root case (0.23). Conclusion: the remaining fix is not a local scaling change; it needs a redesigned globalisation (a properly normed least-squares/trust-region formulation with a step bound proved to accept a scale-invariant step, or the NLEQ-ERR natural-monotonicity test implemented exactly as published), developed against the 14-case matrix above with the XBV-431 cases (roots up to 1e8) kept green. The half-day estimate in D21 was too optimistic: budget 1-2 days. Until then the finding stays open, and the help documents the current single documented profile.

- **D23** (2026-11-24, XBV-434 float32 libm contract: interpreter = C at <= 1 ULP, sqrt exact): Measured, not assumed (32768 float32 arguments per function, gcc 12 -O2, glibc 2.36 builtins so no FMA contraction): fround(Math.fn(x)) differs from the C float function on 326/32768 arguments for sinf, 532 cosf, 24 expf, 110 logf, 2654 powf, 1214 atanf, 2480 asinf and 8756 tanhf (tanh by up to 2 ULP), always by at most 1 float32 ULP; sqrtf is exact on every argument. A 0-ULP libm contract would need a float-libm shim that reproduces glibc bit for bit (a table or a port of its algorithms); that is explicitly NOT taken here. Math.pow is not an oracle for powf. - **D24** (2026-11-24, XBV-436 WP-B2: two published globalisations measured outside the engine -- neither reaches the far root): Measured, not argued (scripts/xbridges-verification/loopLab.ts, npx tsx, committed 3ba4cb8). The lab works on a black-box F(z) of the engine's real loop, with the engine's own finite-difference Jacobian and its Gauss-Seidel pre-passes, so a candidate starts where the engine starts. The loop has THREE unknowns (s, p, u = the gain output); collapsing y = c + y - k y^2 to the one-variable y = 1 + y is a one-step exact solve and is NOT what the engine solves. Candidates: NLEQ-ERR (Deuflhard: natural monotonicity in scaled variables, prediction/correction of lambda, lambda_min fallback) and a Powell dogleg trust region on the scaled merit with D_j = max(D_j, |z_j|, 1). RESULT at algTol 1e-6 / maxIter 100, both wirings: from the engine's zero start NLEQ-ERR converges on 2 of 12 far-root cases (the root-1e3 pair) and dogleg on 0 of 12; from 0.9 x the root both reach 2 of 12 under the engine's solution test (residual AND Newton correction within algTol, XBV-421). Per the plan's own stopping rule (WP-B2: if neither candidate is green, stop and report, do not tune constants per case) the port into the engine (WP-B3) was NOT started and the engine is unchanged. WHY: the equations s_out = c + s - u, p_out = s s and u_out = k p give a structurally rank-deficient Jacobian (rows 1 and 3 are the same equation), so the residual's leading term lies in the range of J and the natural monotonicity ratio |dz_bar|/|dz| tends to 1 from ABOVE as lambda -> 0, never meeting (1 - lambda/4); measured on root 1e7 it is 4.6e9 at lambda 0.5, 2.9e8 at 0.125 and 4.0e10 at 1e-6. The dogleg makes progress only while its region is small (|du| ~ 0.25) and then stalls at a scaled residual of 0.33, for the same reason. The obstacle is therefore not the damping strategy but the rank-deficient start: any repair has to use the residual's structure (eliminate p or u analytically) rather than a better step rule. Three defects in the prototypes were found by measuring and are recorded in the file: the missing Gauss-Seidel pre-passes; a lambda growth capped by mu instead of min(1, 4 lambda), which pinned lambda at 0.125 and made the iteration linear; and an acceptance that passed a 10 %-wrong s, because a residual of 0.19 over |s| = 9e6 is 2e-8 in the scaled norm. XBV-436 stays OPEN, now with this negative result on record so it is not attempted again as a local scaling change.
